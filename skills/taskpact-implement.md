# taskpact: 自主实现

按合约中的完成条件逐条实现功能。

用户已经离开。你需要自主完成所有工作。

## 核心原则

**合约文件（不是对话历史）是 source of truth。**

**铁律：没有通过测试的场景，不算完成。**

四重约束——动手写代码之前必须读完：
1. **项目原则** — config.md 中的全局规则，所有合约都必须遵守
2. **已定决策** — 怎么做（已确定的技术选择，不需要你再做判断）
3. **边界** — 碰什么（允许修改的路径 + 禁止修改的路径）
4. **完成条件** — 什么时候算完（BDD 场景，每个场景有优先级和验证方式）

## 输入

用户调用 `/taskpact-implement`，可选指定合约名。

### 合约选择

```
1. 如果用户指定了合约名 → 直接使用
2. 扫描 .spec/contracts/ 下所有合约，筛选 status 为 agreed 或 in_progress 的
3. 只有一个候选 → 自动选中
4. 有多个候选 → 列出合约名和 status，让用户选
5. 没有候选 → 告诉用户 "没有可实现的合约，请先运行 /taskpact-clarify"
```

**选中后必须报告：** "使用合约: xxx (status: agreed)"

## 启动

```
1. 找到目标合约文件，读取全部内容
2. 读取 .spec/config.md → 获取构建命令、测试命令、单测命令、项目原则
3. 检查 status:
   - agreed       → 首次实现，把合约 frontmatter 的 status 更新为 in_progress
   - in_progress  → 继续实现（可能有验证记录，见"修复模式"）
   - needs-review → 之前判过需人工介入。除非用户明确要你继续，否则停下来说明情况
   - 其他         → 停止，状态不对
4. 列出所有场景，按优先级和依赖关系确定实现顺序:
   - [必须] 场景优先，全部完成才算可交付
   - [应该] 场景其次，尽量完成
   - [可选] 场景最后，有余力再做
```

**状态只写在合约 frontmatter 里。** config.md 不记"当前阶段"——避免两套状态漂移。合约的 status 就是唯一真相。

**必须在写第一行代码之前完成启动。**

---

## 逐场景实现

按优先级顺序逐个实现。每个场景走完整个流程再进入下一个。

**单个场景的完整流程：**

```
1. 读取场景的 假设/当/那么 描述，理解清楚要做什么
2. 检查 已定决策 和 边界 → 确认实现方式和可修改的文件范围
3. 写代码
   - 严格遵守边界中的路径限制
   - 严格使用已定决策中的技术选择
   - 遵守 config.md 中的项目原则
4. 处理测试
   - 场景有 `测试:` 字段 → 确保该测试函数存在，函数名与合约**完全一致**，覆盖场景描述的全部断言
   - 场景没有 `测试:` 字段且非代码审查 → 创建测试，将函数名回填到合约
5. 用 config.md 的单测命令运行该场景的测试 → 必须通过
6. 运行构建命令 → 必须通过
7. git add + git commit（提交信息: [taskpact] 实现场景: <场景名>）
```

**不要跳步。不要批量实现多个场景再一起测试。一个场景一个提交。**

## 修复模式

如果合约已有 `## 验证记录` 且包含 fail 的场景，说明之前有人验证过并写回了结果。此时只修复 fail 的场景：

```
1. 读取验证记录，找到所有 fail 场景和失败原因
2. 失败原因格式：期望什么、实际什么、问题在哪个文件哪一行
3. 根据失败原因直接定位问题并修复
4. 不动 pass 场景的代码（除非修复 fail 必须改）
5. 修复后运行该场景的测试 → 必须通过
6. 运行全量测试 → 确认没有回归
7. git commit（提交信息: [taskpact] 修复场景: <场景名>）
```

**关键规则：不修改完成条件的场景描述和验收标准。元数据（测试函数名、阻塞原因、验证记录）可以写入。**

## 自验证

所有场景实现/修复完成后，你必须自己跑一轮完整验证。**你交付的必须是能通过验证的结果。**

```
1. 运行构建命令 → 必须通过
2. 运行全量测试 → 必须通过
3. 逐场景确认：
   - 有 `测试:` 字段 → 用单测命令运行，确认通过
   - 有 `验证方式: 代码审查` → 读代码确认符合场景描述
   - [应该/可选] 场景未实现 → 标记 skip
   - 记录每个场景的结果（pass / fail / skip / uncertain）
4. 以用户身份实际运行产出物，确认核心功能可用
   - 这不是建议，是必须执行的步骤
   - 运行产出物的真实入口（启动服务、执行命令、打开页面等）
   - 验证 [必须] 场景对应的功能确实能用
   - 在验证记录中写明你运行了什么、结果是什么
5. 逐条核对项目原则（config.md 的「## 项目原则」）
   - 把每一条原则单独拎出来，对照本次改动逐条判定：满足 / 违反 / 不适用 / uncertain
   - 违反的当场修复，不能只在记录里"记一笔"就放过
   - 判不准是否满足的标 uncertain，按第 7 步 status 规则处理
6. 写入验证记录（来源: 自验证），包含两部分：
   - 场景结果：逐场景 pass / fail / skip / uncertain
   - 原则核对：逐条列出每条项目原则及判定（满足 / 违反 / 不适用 / uncertain）
7. 判定 status（写入合约 frontmatter）:
   - 所有 [必须] 场景 pass，没有 [必须] 场景是 fail 或 uncertain，且没有项目原则被违反或 uncertain → status: done
   - 有 [必须] 场景 fail，或有项目原则被违反 → 回到修复模式，修完再跑一轮自验证（status 保持 in_progress）
   - 有 [必须] 场景 uncertain，或有项目原则 uncertain（你无法确定是否满足）→ status: needs-review，验证记录里清楚写明哪个场景/哪条原则、为什么无法确定。【不要置 done】
   - 非必须场景的 uncertain/skip → 不阻塞 done，但要在验证记录里列出
   - round 已达 max_rounds 仍有 [必须] fail → status: needs-review，说明已尽最大轮次
8. git commit（提交信息: [taskpact] 实现完成: <合约名>  或  [taskpact] 需人工介入: <合约名>）
```

**为什么 uncertain 的 [必须] 场景不能置 done：** done 是"绿灯可信"的承诺。如果一个必须场景你都拿不准是否满足，置 done 等于把不确定性藏起来骗用户。诚实地转 needs-review，让人来拍板。

用户后续运行 `/taskpact-verify` 是独立的交叉验证。

## 遇到阻塞

如果某个场景无法实现（依赖缺失、需求矛盾、测试始终无法通过）：

```
1. 在合约该场景下方写一行: 阻塞原因: <具体原因>
2. git commit（提交信息: [taskpact] 阻塞场景: <场景名>）
3. 跳过，继续下一个场景
4. 如果被阻塞的是 [必须] 场景，自验证时该合约判 needs-review
```

## 上下文管理

你的上下文窗口有限。合约文件在磁盘上，不受上下文压缩影响。

**合约文件是你的外部记忆。随时保持它是最新的。**

### 恢复协议

如果你感觉上下文被压缩了，或者用户 clear 后重新调用了 implement，立即执行：

```
1. 读取 config.md → 构建/测试/单测命令 + 项目原则
2. 扫描 .spec/contracts/ → 找 status 为 in_progress / agreed 的活跃合约
3. 读取合约文件 → 获取场景列表、当前 status、验证记录
4. 查看 git log → 找 [taskpact] 开头的提交，知道自己做到哪了
5. 对比场景列表和已提交的场景 → 确定下一个未完成的场景
6. 继续实现
```

**不要依赖对话记忆。一切以 config.md、合约文件和代码为准。**

## 常见错误

| 你可能犯的错误 | 正确做法 |
|--------------|---------|
| 没读完合约就开始写代码 | 启动步骤必须完整执行 |
| 修改了禁止修改的文件 | 每次改文件前检查边界 |
| 场景没有通过测试就提交了 | 铁律：必须有通过的测试 |
| 只跑了单测没跑构建 | 每个场景：测试 + 构建都通过 |
| 上下文压缩后凭记忆继续 | 立即执行恢复协议 |
| 修复 fail 时改了 pass 的代码 | 最小化修复，改完跑全量测试 |
| 凭直觉判断 pass/fail | 必须通过运行测试或代码审查来验证 |
| 一次实现多个场景再提交 | 一个场景一个提交 |
| 测试函数名和合约不一致 | 合约写什么名就用什么名 |
| 偏离合约，加了没要求的功能 | 只做合约要求的，多余的不做 |
| 修复时降低合约标准 | 修代码，不改场景描述和验收标准 |
| 实现完就交差，没跑自验证 | 必须跑完自验证再交付 |
| [必须] 场景拿不准却置 done | 转 needs-review，让人来判 |
| 项目原则没逐条核对就置 done | 自验证里逐条核对每条原则，违反必修、结果写进验证记录 |
